Desktop software is a long conversation

8 October 2026 · 4 min read

Most of my engineering work has been Windows desktop software for precision equipment. C++ and C# were the daily tools. The interesting part was rarely a single screen. It was the stretch from a prototype, through testing and feature evaluation, to a build a colleague could ship and later support.

A desktop application for a precise machine has a long memory. Someone will open it on an ordinary Tuesday, months after the demo, and expect last month’s workflow to behave. That changes the design. A clever interaction is useless if the manual and the software disagree, or if the next engineer cannot see why a limit was set where it was.

So the job was never only code. I wrote technical specifications, system integration guides, and user manuals, and I stayed with the software after launch. Documentation was how the team kept the product when the people who built a feature moved on to the next one.

I also led cross-functional work with PMP practice: requirements, schedules, and the engineering problems that ignore the schedule. The useful habit was to keep both visible. A date with no technical risk is a wish. A careful design with no release is still a prototype.

I still like this kind of software. It has users you can talk to, a machine you can point at, and a definition of done that is physical. The equipment does what the person asked.
